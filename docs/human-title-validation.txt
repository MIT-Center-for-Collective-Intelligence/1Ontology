HUMAN TITLE REVIEW — FIVE-CASE STAFF TRY-OUT
Implementation date: 2026-10-15

Purpose
This is the small usability try-out discussed in the October 15 meeting, not
the final validation study. It reuses completed GPT-6.1 Sol title proposals.
The app makes no model requests and has no operation that changes ontology
content or existing review datasets, answers, or event histories.

Reviewer workflow
1. Each case has one assigned human creator. The creator sees the original
   title and full single O*NET description, without model output or siblings.
2. All creators finish their independent titles before any comparisons open.
3. Other reviewers assess and rank original/model/human alternatives. Creators
   never evaluate their own cases. Model and human source labels are hidden;
   alternative order rotates reproducibly. Exact matching title sets appear
   once, including sets whose title order differs. Ties and uncertainty differ.
4. Confidence, comments, active browser time, and elapsed server time are kept.
   Drafts survive refresh; pausing hides the task and stops the active timer.
   Submitted answers are immutable. Delivery retries reuse one frozen payload.
5. Coordinators see progress. A participating coordinator cannot see team
   answers, source comparisons, or exports until all evaluations finish or the
   study closes. A coordinator outside the reviewer roster can monitor interim
   patterns. Exports preserve individual answers, prompt, source provenance,
   dataset version, and original/model/human identity.

Scientific limits and open decisions
- The original title remains visible to identify the target activity inside
  a multi-activity source sentence. The original alternative is recognizable;
  this is source-blinding of human/model answers, not full three-way blinding.
- The five cases are deterministic examples: 2 Keep, 2 Clarify, 1 Split. They
  are deliberately not a representative sample. Prior staff exposure to some
  model outputs prevents interpreting this try-out as independent accuracy.
- Adequate/needs work/unsure, preference ranks with ties, overall confidence
  1–5, and optional comments (required for concerns) are provisional settings.
  Final questions, sample design, sample size, reviewer roster, acceptance
  criteria, adjudication, and any time limits require the team's agreement.
- Human titles are comparators, not gold labels. Identical alternatives share
  judgments attributed to every matching source; source columns are dependent.
  Counts are not population accuracy estimates. No significance-driven stop,
  automatic ontology approval, or semantic-correctness claim is implemented.
- The engine supports up to 200 cases. Only the five-case package is supplied.
  A 99-case/3-reviewer plan assigns each reviewer 33 creations and 66 evaluations.

Local preview
Install isolated dependencies with npm ci --legacy-peer-deps --ignore-scripts.
Use an existing ignored environment file; never print or commit its contents.
Set TITLE_VALIDATION_ENV_FILE to that file, then run:
  node scripts/som-review/run-title-validation-local.cjs dev
Open http://127.0.0.1:3105/review/title-validation
Three preview identities share local development-only study data; switch the
identity selector to exercise assignments. Do not use it for human research.
Storage: ignored .title-validation-preview/ with append-only event journal.
To prepare a clean try-out after software QA, stop the server and MOVE the
entire preview directory to a dated archive; never overwrite research answers.
The next launch creates a fresh development study. Saved browser drafts use
separate opaque reviewer keys. Production never accepts preview identities.
Loopback preview requires development mode, explicit flag, loopback Host AND
TCP peer, and same-origin requests. Local writes use process and file locks.

Production release procedure
1. Agree the provisional pilot procedure and reviewer roster. Present the
   five-case package before publishing/activating this new semantic dataset.
2. Verify deployed Firestore client rules deny direct client read/write of
   titleValidationStudiesV1/{study} and all answers/events subcollections.
   Rules are not versioned in this repository. Admin API uses verified Firebase
   bearer tokens, revoked-token checks, coordinator authorization, and isolated
   transactions; broad client rules would bypass that API protection.
   The October 15 release checked ruleset
   986c6e5d-f1b8-46c7-814c-e0da893a0e8b using 46 simulated requests:
   all 45 study/answer/event access attempts were denied, including signed-in
   reviewers and coordinators; the allowed positive control also passed.
   This evaluation did not write documents or change rules/permissions.
3. Merge the reviewed, tested source through main using the existing deployment
   process. Do not deploy uncommitted code or from the older dirty checkout.
   Retain the existing review dataset-selection and prompt-trace tests/fixes.
4. The reviewed Cloud Build configuration enables TITLE_VALIDATION_RELEASED=1
   for this five-case staff pilot. The release identity and promotion checks
   verify its exact package hash and flag, page route, and anonymous API denial
   before and after promotion. There is no automatic reviewer enrollment.
5. Coordinator opens /review/title-validation, enters 3–10 existing ontology
   account emails and display names, creates a DRAFT study, then opens it.
   Production collection: titleValidationStudiesV1, separate from legacy reviews.
6. Verify real production login, roster access, assignment, source hiding,
   immutable saves, prompt disclosure after closure, and preserved legacy data
   on desktop and compact widths. Record main SHA, Cloud Run revision, dataset
   version, results, and rollback revision before inviting reviewers.
   The existing verified oneweb@umich.edu ontology account has coordinator
   access. A coordinator creates a draft using the agreed existing accounts;
   deployment itself neither creates a study nor assigns anyone to it.

Interface and accessibility
The review route has scoped light and dark themes following the user's saved
platform profile preference. Desktop uses a sticky source panel
beside the form; compact screens use one column. Choice styling is identical
for every alternative. Draft recovery/storage failure, successful saves,
uncertain delivery, and coordinator actions have visible status messages.
Validation focuses the relevant visible control. Split-row removal preserves
neighboring values and focus. The close action uses an accessible confirmation.
No scientific instructions, output data, or saved responses were revised by
the visual redesign.

The coordinator's own review copy
The coordinator can open /review/title-validation?workspace=practice using
normal ontology sign-in. This creates a separate owner-scoped practice study
with the same five frozen examples. It does not enroll the coordinator in the
staff pilot or read/copy the staff's answers. The coordinator writes titles for
all five activities, then compares alternatives for all five, with no role
selection or waiting for other people. These are interface-testing responses, not independent
human judgments or validation results. Practice keeps separate drafts, answers,
presentation timestamps, and event history; it never resets saved progress.

The API verifies the existing token and coordinator permission, derives the
practice ID from the authenticated owner. The three historical synthetic role
keys remain internal storage identities so all earlier answers, drafts, seeds,
and events are preserved. The server chooses the next task and its storage key;
clients cannot select an internal role. Valid legacy synthetic role fields are
ignored and invalid ones rejected. Progress counts completed activities once,
including when an older copy has multiple evaluations for one activity.
Each practice study carries purpose=interface-practice and its owner.
Normal endpoints reject practice-prefixed studies; practice requests ignore
client-supplied study IDs, reject mismatched ownership, and deny management,
dashboard, and export operations. Synthetic roles are not Firebase accounts.
No credentials, auth claims, source data, or model proposals are generated.
Production candidate checks cover both workspace pages and anonymous denials.

Rollback: disable TITLE_VALIDATION_RELEASED and restore the previous committed
Cloud Run revision if necessary. Never delete the new study collection or old
review history as a rollback mechanism.
